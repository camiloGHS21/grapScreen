## Objetivo
Acercar el editor de flujos de grapScreen a la ergonomía de n8n **sin tocar Rust**,
manteniendo la identidad visual propia (paleta violeta/roja, sidebar, temas).

## Diagnóstico previo
El motor de grafos Rust (`src-tauri/src/application/graph_executor/`) ya soporta
condition/switch/loop/merge/split_batches/wait/error_handler/sub_workflow y HTTP
Request real. La brecha era de capa de producto (UI), no de motor.

Editor/Executions/Evaluations, botón Execute, consola de Logs, expresiones

## Decisiones de diseño (importantes)
- **Credencial es aditiva**: sin `credential_id` el flujo se comporta igual que
  antes. La búsqueda es best-effort (avisa por `warn_ui` si no existe).
- **Thread-local con save/restore** para que un sub-workflow no filtre las
  credenciales del padre.
- **`compare_datasets` empareja por string**: `1` y `"1"` colapsan en la misma
  clave (`expressions::stringify`). Los items de salida llevan `change_type`,
  `key`, `current` y `previous`.
- **Fallback de `key_of`**: si el path de la clave es `null` sobre un item, se usa
  el valor escalar del propio item. Sin esto, un `compare_with` en texto plano
  (líneas) colapsaba todos los items en la clave vacía y todos salían como
  "removed". Bug real detectado por los tests.
- **Dedupe preserva el orden original en ambos modos**: `keep: last` sustituye el
  contenido en la posición de la primera aparición, no lo mueve al final.
- **Extracción tolerante**: `extract_json_object` busca el `{...}` balanceado más
  externo ignorando llaves dentro de strings, y desenvuelve fences markdown.
- **Sentimiento posicional**: primera etiqueta = 1, última = -1, intermedias
  interpoladas; etiqueta desconocida = 0 (no falla).

## ⚠️ Gotcha crítico de Windows: `cargo test` falla con exit 127 sin output
- Síntoma: `cargo test --lib` termina con `exit code 127` /
  `0xC0000139 STATUS_ENTRYPOINT_NOT_FOUND` y NO imprime nada. No es un fallo de
  compilación.
- Causa raíz: el crate `windows` activa `Win32_UI_WindowsAndMessaging`, así que
  el linker emite un import estático de `COMCTL32.dll`. Los binarios de test de
  Rust NO llevan sección de recursos, así que el loader lo enlaza contra el
  comctl32 v5.82 legacy de `System32`, que **no exporta `TaskDialogIndirect`**.
  El proceso muere antes de `main`.
- Diagnóstico: `dumpbin /dependents` + `mt.exe -inputresource:...;#1` (revela "el
  archivo imagen no contenía sección de recursos"). Reproducible con un programa
  Rust de 10 líneas que declare `#[link(name = "comctl32")]`.
- Solución: `scripts/test.ps1` compila con `--no-run`, embebe
  `src-tauri/comctl.manifest` (dependencia de Common-Controls **v6**) con
  `mt.exe`, y luego ejecuta. Verificado: `rc=0` tras embeber, `127` antes.
- **No se puede hacer desde `build.rs`**: el build script corre ANTES del link,
  así que el binario de test aún no existe.

# Cierre de Fase 4 — skill reutilizable del workaround de Windows

Se empaquetó el workaround del manifest como skill reutilizable en
`~/.workbuddy-ai/skills/windows-rust-test-manifest/` (SKILL.md +
`scripts/embed-test-manifest.ps1` + `references/diagnosis-notes.md`), validada
con `quick_validate.py`.

## Lecciones nuevas descubiertas al generalizar el script

Al portar `scripts/test.ps1` a un script reutilizable aparecieron tres fallos
que el script original tenía latentes:

1. **`$LASTEXITCODE` puede ser `$null` en este host.** `$null -ne 0` evalúa a
   `$TRUE`, así que el guard `if ($LASTEXITCODE -ne 0) { exit }` abortaba
   corridas correctas: el script imprimía el primer banner y terminaba sin
   error visible. Arreglado con `Get-LastExitCode` que normaliza `$null → 0`.

2. **`${env:ProgramFiles(x86)}` expande a cadena vacía** en este host → el path
   del SDK quedaba como `\Windows Kits\10\bin`, `Test-Path` daba false, y
   `mt.exe` nunca se localizaba (por tanto el parcheo se saltaba en silencio,
   haciendo que el bug pareciera irresoluble). Arreglado probando
   `[Environment]::GetEnvironmentVariable("ProgramFiles(x86)")` y dos rutas
   literales de fallback.

3. **`cargo test` después de parchear deshace el parche.** Cargo re-linkea el
   binario de test si lo considera obsoleto, y el link nuevo no lleva sección de
   recursos → vuelve el `0xC0000139`. Cargo ahora lo reporta explícitamente:
   `process didn't exit successfully: ... (exit code: 0xc0000139,
   STATUS_ENTRYPOINT_NOT_FOUND)`. Solución: el paso de ejecución invoca el
   binario parcheado **directamente**, nunca `cargo test`. Lo mismo aplica a
   tocar fuentes entre parchear y ejecutar.

`scripts/test.ps1` del proyecto se actualizó con las tres correcciones.

## Verificación A/B final (medida)

| Etapa | Timestamp | Tamaño | Resultado |
|---|---|---|---|
| Build fresco, sin manifest | 12:58:25 | 5.429.760 B | exit **127**, sin output |
| Tras `mt.exe` | 12:59:19 | 5.430.272 B | exit **0**, `92 passed; 0 failed` |

El crecimiento de ~512 B es la sección de recursos añadida; comprobarlo es la

## Nota de entorno
La herramienta de PowerShell en este host **no ejecuta subprocesos nativos**:
llamar a `mt.exe` (o `cargo`) a través de ella no hace nada — el tamaño del
binario no cambia y `$LASTEXITCODE` queda vacío. El mismo comando desde Bash
funciona a la primera. Consecuencia práctica: los scripts `.ps1` de este repo
(como `scripts/test.ps1`) parecen "pararse sin motivo" cuando se lanzan desde
esa herramienta. **Verificar/depurar este flujo desde Bash**, no desde
PowerShell. `Start-Process` y `[Diagnostics.Process]::Start` están bloqueados
por seguridad, así que tampoco sirven como alternativa.

Secuencia manual verificada desde Bash (build → `mt.exe` → ejecutar binario):
tamaño 5.429.760 → 5.430.272 B, exit 127 → 0, `92 passed; 0 failed`.

# Fase 5 — Cliente HTTP nativo (sustituir `curl`)

Objetivo: quitar la dependencia del binario `curl` del sistema en todo el motor.

## Qué se hizo

- **Nuevo** `application/http_client.rs`: envuelve `reqwest` (blocking,
  `rustls-tls`, `json`) y expone helpers puros testeables sin red.
- `replay_helpers/executors.rs` → `execute_http_request` reescrito sobre el
  cliente nativo. Se conserva el contrato de salida: `<var>` con el body y
  `<var>_status` con el código.
- `graph_executor/ai_nodes.rs` → `call_chat` usa el cliente. Los 4 nodos IA
  (Cadena LLM, Clasificador, Extraer información, Sentimiento) comparten esa
  ruta, así que un solo cambio los cubre todos.
- `integration_ai.rs`, `integration_google.rs`, `integration_social.rs` →
  migrados a `http_client::post_json`. Los que antes ignoraban el resultado
  (`google_sheets`, `google_docs`, `telegram`, `whatsapp`) ahora comprueban la
  respuesta y avisan con el status.
- `Cargo.toml`: `reqwest = { version = "0.12", default-features = false,
  features = ["blocking", "json", "rustls-tls"] }`. No hizo falta tocar el
  binario: reqwest ya estaba en el árbol vía Tauri.

## Decisiones de diseño

- **`no_proxy()` explícito.** reqwest hereda `http_proxy`/`HTTPS_PROXY` del
  entorno. El `curl` anterior no pasaba `-x`, así que iba directo. Este fue un
  bug real descubierto por un test: en este entorno hay un proxy de sandbox en
  `127.0.0.1:27418` que convertía una conexión rechazada en `502 Bad Gateway`,
  enmascarando el error real.
- **rustls** en lugar de native-tls, para no depender de OpenSSL del sistema.
- **Basic auth como cabecera real** (`Authorization: Basic <base64>`), no el
  marcador `\0basic\0` que existía sólo para pasar `--user` a curl.
- **Non-2xx no es éxito**, pero sigue exponiendo body y status igual que antes.
- Las cabeceras del nodo ganan sobre las de la credencial, case-insensitive.

## Errores resueltos

1. `?` no convertía `String` a `HttpError` → envolver el `format!` en
   `HttpError::Transport`.
2. Quité el import de `Command` en `integration_social.rs` pero seguía usándose
   para abrir el navegador en la ruta de WhatsApp Web → restaurado con comentario.
3. **Bug real en el desempaquetado de errores**: recorría la cadena de `source`
   quedándose con el mensaje MÁS PROFUNDO (`upstream connect failed`), el menos
   útil. Corregido para quedarse con el más superficial e informativo.
4. 3 tests fallaban: dos por expectativas mías incorrectas (el prefijo de una
   credencial se recorta con `trim()`; el `{` de un JSON roto forma parte del
   nombre al dividir en el primer `:`) y uno por el bug del proxy.

## Verificación

# Fase 6 — Nodos de base de datos SQLite

## Qué se hizo

- **Nuevo** `graph_executor/db_nodes.rs`: runners `sqlite_query` (SELECT) y
  `sqlite_execute` (INSERT/UPDATE/DELETE/DDL) sobre `rusqlite` con feature
  `bundled` (compila SQLite desde fuente, sin depender de DLL del sistema).
- `Cargo.toml`: `rusqlite = { version = "0.32", features = ["bundled"] }`.
- Registro en motor: `TRANSFORM_KINDS` + `ITEM_AWARE_KINDS` + dispatch en
  `node_runners.rs`.
- Frontend wiring completo siguiendo la checklist del proyecto:
  `types.ts`, `nodeCatalog.ts`, `nodeCategories.ts`, `nodePorts.ts`,
  `Flowchart.tsx` (color `#10b981`), `buildNodes.ts`, `eventModifiers.ts`,
  `addCategories.tsx`, `nodeStatePopulator.ts`, `useFlowchartEditState.ts`,
  `useFlowchartEdit.ts`, `ControlForms.tsx`, `NodeEditModal.tsx`.

## Decisiones de diseño

- **Dos nodos separados** (Consulta / Ejecutar) en lugar de uno con modo.
  Un query *reemplaza* el item list con sus filas; un execute deja la lista
  intacta y devuelve un solo item con `changes` + `last_insert_id`. Mezclar
  ambos comportamientos en un nodo forzaría una decisión en tiempo de ejecución.
- **Parámetros vinculados**, nunca interpolados en el string SQL. El campo
  `params` acepta JSON array `[1, "ana"]` (posicional `?`) u objeto
  `{ "id": 7 }` (named `:id`). Esto previene inyección SQL cuando el valor
  viene de una expresión como `{{ $json.text }}`.
- **Rutas relativas ancladas** a `Documentos/automateScreen/databases`, para
  que un flujo que diga `clientes.db` funcione igual en cualquier máquina.
  Rutas absolutas se usan tal cual.
- **Conexión de solo lectura** para `sqlite_query`: si el fichero no existe
  falla en lugar de crear una base vacía (que ocultaría un error de config).
  `sqlite_execute` crea el fichero y los directorios intermedios si hace falta.
- **BLOBs como base64**: las celdas BLOB se serializan en base64 para que
  sobrevivan al modelo de items y sean consumibles por nodos downstream.
- **Named params con objeto JSON**: rusqlite 0.32 no soporta named params en
  la API raw, así que se vinculan posicionalmente en el orden de iteración del
  objeto. El test documenta este comportamiento.

## Errores resueltos

1. Fichero `db_nodes.rs` creado en `application/` en vez de
   `graph_executor/` → movido, `mod.rs` ya apuntaba bien.
2. `raw_bind_parameter` de rusqlite usa índices `usize` (1-based), no strings.
   Corregido tanto en `bind_query_params` como en `bind_params_and_run`.
3. `stmt.execute(&refs)` con `Vec<(&str, &dyn ToSql)>` intentaba named params,
   que rusqlite 0.32 rechaza para nombres cortos. Cambiado a
   `raw_bind_parameter` posicional para todo.
4. **Colisión de tablas entre tests**: `temp_db` usaba `std::process::id()`
   como parte del directorio, así que todos los tests compartían la misma ruta.
   Añadí un timestamp de nanosegundos para hacer cada directorio único.
5. `execute_delete` devolvía `changes: 0` porque `bind_params` descartaba el
   valor de retorno de `execute`. Cambiado a `bind_params_and_run` que devuelve
   `usize` (filas afectadas).
6. `execute_can_create_a_table` esperaba `changes: 1` para `CREATE TABLE`, pero
   DDL modifica 0 filas. Corregida la expectativa.
7. `execute_reports_binding_mismatch` esperaba que 2 placeholders + 1
   parámetro fallara, pero SQLite vincula el segundo como NULL y la inserción
   tiene éxito. Convertido en un test positivo que verifica el comportamiento.

## 🔴 BUG REAL encontrado y arreglado: el payload del trigger se perdía

**Síntoma**: los triggers `webhook` y `polling` disparaban el flujo, pero el

**Causa** (orden de llamadas):
1. `replay_service/event_runner.rs:32` — el daemon siembra el payload con

3. `graph_executor/mod.rs` — lo primero que hacía era

### 3. ⚠️ Trampa encontrada: el nodo `app` NO es passthrough

Escribí un test de invariante «todo `ENTRY_KINDS` está en `PASSTHROUGH_KINDS»` y
**falló**: `app` está en `ENTRY_KINDS` pero no en `PASSTHROUGH_KINDS`.

**No es un bug.** `buildNodes.ts` construye el nodo `app` con
`start: 0, end: events.length - 1`: es la raíz de toda **grabación de pantalla** y
posee el rango completo de eventos, que el motor reproduce vía `exec_range`.
Si se «arreglara» añadiéndolo a `PASSTHROUGH_KINDS`, **todas las grabaciones
dejarían de reproducirse sin ningún error** — justo lo que el usuario pidió no
romper. El test se reescribió para codificar el invariante real
(`every_entry_kind_passes_through_or_owns_a_recorded_range`, con `app` como
excepción documentada) y se añadió
`the_app_node_must_replay_its_recorded_range` para que ese «arreglo» falle ruidoso.
