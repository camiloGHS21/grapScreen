## "no se ve bien los nodos" — la tarjeta de nodo estaba colapsada (NODE_W)

**Síntoma**: el nodo del canvas se veía como un cuadradito con el icono y UNA sola
letra ("W", "d") en lugar de una tarjeta con su nombre.

**Causa raíz**: `src/Flowchart.tsx` exportaba `NODE_W = 104` y `FlowchartNode`
aplica ese valor como `width` **inline**:
`style={{ width: NODE_W, height: dynamicH }}`. El CSS `.n8n-node` declara
`width: 240px`, pero **el inline gana**, así que la tarjeta medía 104px reales
mientras su padding horizontal era de ~50-58px → quedaban ~10-46px para el
texto, menos que el propio icono (34-40px) + gap. El nombre se recortaba a un
carácter y el subtítulo desaparecía.

Los dos valores eran **originales** del primer commit (`git show HEAD`): el CSS
`.n8n-node { width: 240px; padding: 12px 42px 12px 16px }` está escrito
claramente para una tarjeta de 240px (icono 38px + gap 12 → 132px de texto), y
`NODE_W = 104` lo contradecía. El nodo nunca se renderizó bien; por eso el
usuario ya se había quejado antes de que "los nodos no se ven como los de n8n".

**Arreglo**: `NODE_W = 104` → `240`, con un comentario que explica que este
constante es a la vez la geometría del canvas y el `width` de la tarjeta, así que
debe seguir sincronizado con la regla `.n8n-node` de `styles.css`.

**Por qué 240 y no rediseñar a cuadrado**: `NODE_W` es la única fuente de verdad
de la anchura y la usan TODOS los consumidores de geometría, así que cambiarla es
consistente por construcción:
- `FlowchartNode.tsx` → `width: NODE_W` (la tarjeta)
- `FlowchartNodeGroup.tsx` → extremos de los cables `pos.x + NODE_W`
- `FlowchartCanvas.tsx`, `useWorkspaceActions.ts` → mismo cálculo
- `Minimap.tsx` → `NODE_W * scale`
- `useFlowchartWorkspace.ts` → espaciado por defecto `NODE_W + 100`
- `useFlowchartEventListeners.ts`, `useFlowchartLayoutHelpers.ts` → límites
- `Flowchart.tsx` `findFreeSpot` → `COL_STEP = NODE_W + 70`, `OVERLAP_X = NODE_W + 20`
Los puertos van con `left/right: -8px`, así que siguen el ancho automáticamente.
No hay ningún otro 104 hardcodeado en `src/`.

**Ojo con layouts guardados**: las posiciones guardadas se calcularon para nodos
de 104px, así que al abrir una automatización vieja los nodos pueden solaparse.
Los nuevos se colocan bien porque `findFreeSpot` deriva de `NODE_W`.

## "Trigger On" de WhatsApp Trigger: n8n NO trae valor por defecto (verificado)

El usuario insistió: "en n8n hay trigger por defecto en mi app no cuadra".
Se verificó contra TRES fuentes, todas coinciden:

1. Fuente local cacheada `.n8n-cache/src/packages/nodes-base/nodes/WhatsApp/WhatsAppTrigger.node.ts`
   (versión reciente, ya tiene `builderHint` y `NodeConnectionTypes`):
   `{ displayName: 'Trigger On', name: 'updates', type: 'multiOptions', required: true, default: [] }`
2. **GitHub master** (raw.githubusercontent.com, `packages/nodes-base/nodes/WhatsApp/WhatsAppTrigger.node.ts`):
   idéntico, `default: []`.
3. **Docs oficiales** (docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.whatsapptrigger):
   solo lista los 10 eventos, NO menciona ningún valor por defecto.

El `defaults` del nodo es `{ name: 'WhatsApp Trigger' }` — solo el nombre, ningún parámetro.

**Conclusión**: la extracción es fiel. n8n obliga a elegir: si `updates` va vacío,
`fields: JSON.stringify([])` registra una suscripción sin campos, así que el
trigger no se dispararía. No es un bug nuestro.

**Por qué el usuario lo cree**: n8n marca el campo vacío de forma más discreta
(su placeholder es "Select…"), y sus **plantillas** sí traen `updates: ['messages']`
puesto. Ojo también: el nodo declara `subtitle: '={{$parameter["event"]}}'`, que
referencia un parámetro `event` que NO existe (residuo de n8n) — no confundir con
el campo real `updates`.

Pendiente: el usuario debe decidir si quiere (a) preseleccionar "Messages" como
default propio de la app, (b) dejarlo vacío y fiel a n8n, o (c) vacío pero sin el
estilo rojo que añadimos (borde + aviso + punto en la pestaña).

## Decisión del usuario: preseleccionar "Messages" en "Trigger On"

El usuario eligió (preguntado explícitamente) **preseleccionar "Messages"** en vez
de dejar el campo vacío como n8n. Implementado como DATO, no como caso especial:

- **`src/data/n8n-param-defaults.json`** (nuevo): `{ "WhatsAppTrigger": { "updates": ["messages"] } }`.
  Clave = `payload.key` de `public/n8n-params/<key>.json`; campo = `name` de la
  propiedad. Añadir otro override = una línea.
- **`src/features/modals/edit/paramDefaults.ts`** (nuevo): módulo **sin React** con
  `isEmptyValue(v)` (undefined/null/""/[]/{} cuentan como vacío) y
  `applyAppDefaults(nodeKey, config)`, que rellena SOLO los campos vacíos y clona
  los arrays (dos nodos no comparten el mismo array mutable).
  Está separado del .tsx a propósito, para poder ejecutar la lógica sin renderizar.
- **`N8nParamsForm.tsx`**: el sembrado ahora es
  `applyAppDefaults(payload.key, { ...defaults, ...value })` — orden deliberado:
  defaults de n8n → overrides de grapScreen solo si sigue vacío → valor guardado,
  que SIEMPRE gana.

**Efecto secundario bueno**: al quedar `updates` relleno, en el WhatsApp Trigger
desaparecen el borde rojo, el aviso "Obligatorio…" y el punto de la pestaña, que
era justo lo que se veía mal en el pantallazo.

**Verificación real** (no a ojo): se compiló `paramDefaults.ts` con tsc a JS y se
ejecutaron 17 asserts con node → **17/17 ok**: campo ausente, guardado-vacío,
elección guardada simple y múltiple (gana), otros campos/nodos intactos, y que el
array no se comparte entre llamadas. Además, un validador en Python comprueba que
la clave y el campo existen de verdad en `public/n8n-params/WhatsAppTrigger.json`
y que `'messages'` está entre las opciones del campo.

## Barra superior ilegible + "que sea responsive la aplicación"

Petición: *"cudra bien la letra que sale arriba que no se puede leer bien y que sea
responsive la aplicasion"*.

### La causa real no era la que parecía

El nombre del proyecto (`demo_formulario_excel`) no "se solapaba" con el readout:
`.ftb-left` se **encogía** por debajo de su contenido (sus hijos conservan
`min-width: auto` y se niegan a encoger), así que el crumb y el readout se salían
de su grupo y la tira de pestañas — que es `flex-shrink: 0` — quedaba **encima** de
los dos. Medido: a 1082px `.ftb-left` = 106px mientras sus hijos sumaban 380px.

Arreglo en `src/styles.css`:
- `.ftb-crumb` → `overflow: hidden`, `flex: 0 1 auto`.
- `.ftb-crumb-scope` → `min-width: 0` + `text-overflow: ellipsis` (el truco
  clásico: `min-width: auto` es el que impide truncar).
- `.ftb-crumb-sep` → `flex-shrink: 0`.

### Escalera responsive: medida, no adivinada

Primer intento a ojo (corte en 1240/1060) → **mal**: a 1280px el nombre quedaba
aplastado a 1–18px. Se sustituyó por una escalera medida con una sonda DOM:

- `@media (max-width: 1450px)` → `.flow-topbar` con `flex-wrap: wrap`, y `.ftb-tabs`
  baja a su propia fila (`order: 3; width: 100%`).
- `@media (max-width: 980px)` → se oculta el readout (`DURACIÓN/PASOS/VIDEO`).

Resultado a 11 anchos (1600→900): `ALL-OK`. El nombre conserva sus 130px, sin
solapes, sin desbordes; el readout aguanta visible hasta 1006px.

### Armazón: el riel de iconos estaba a medias

A ≤900px (justo el `minWidth` de la ventana) el sidebar colapsa a 86px, pero
**casi todas las etiquetas llevan `font-size` INLINE** (nombre de marca, filas de
proyecto, los dos botones de ajustes, el bloque de usuario). Un estilo inline gana
a cualquier regla de hoja, `!important` incluido → las etiquetas seguían visibles,
se salían de la columna de 86px y **recortaban el logo contra el borde**.

Segunda trampa: las reglas se pusieron en el `@media(max-width:900px)` de la línea
~1021, pero `.sidebar-section-title` (y los botones de ajustes) se **redefinen
después** (línea ~1234) → ganaba la de después. Por eso el bloque autoritativo del
riel va **al final del archivo**, como manda la convención del proyecto.

Arreglo: `.sidebar-user` (clase nueva en `SidebarUserProfile.tsx`) para poder
apuntarlo; etiquetas fuera con `display: none` donde se puede y `font-size: 0
!important` donde solo hay font-size; iconos con `flex: none` y todo centrado;
`aside { padding: 20px 10px }` porque 18px laterales no caben en 86px.

Medido a 8 anchos (1440→760): `brandOver=no`, `docOver=no`, `spill=[]` en todos.

### Cómo se verificó (importante para la próxima vez)

- El **editor no es alcanzable sin backend Tauri**, pero el login es solo
  `localStorage["gs_user"]`. Se sembró con una página servida desde `public/`
  (mismo origen) que hace `location.replace("/")` → headless Chrome captura la app
  real, no el login. **Esos archivos temporales ya se borraron**; si hacen falta
  otra vez, se recrean.
- Para medir la app real se usó un **iframe del mismo origen**: comparte
  `localStorage`, así que la app entra logueada dentro del iframe y se puede leer
  su DOM desde la página padre.
- Sonda de solape **con filas**: comparar `tabs.l < left.r` da falso positivo
  cuando las pestañas bajan a otra fila. Hay que exigir que compartan fila
  (`tabs.top < left.bottom - 4`).
- Contar filas por "número de `top` distintos" **no sirve**: los tres grupos tienen
  alturas distintas y dan 3 filas siempre. Hay que usar la prueba geométrica.

## Iconos fallback cuando la imagen falla

Petición: *"cudralos que todos tenga iconos"*.

Algunos triggers/nodos del catálogo n8n tenían el icono roto (404) y el `onError`
solo ocultaba la imagen (`display: "none"`), dejando un hueco vacío en vez de un
fallback.

### Fix en `FlowSidePanel.tsx` — `PanelItem`

- Se añadió estado local `const [imgFailed, setImgFailed] = useState(false)`.
- Cuando el `<img>` falla (`onError`), ahora se setea `imgFailed = true` y React
  re-renderiza mostrando el fallback:
  1. Si hay `n8nInitial` → badge con la inicial coloreada (ej: "S" para Slack)
  2. Si no hay inicial → icono por defecto de Lucide

Antes: `onError={(e) => { e.currentTarget.style.display = "none"; }}` → hueco vacío
Después: `onError={() => setImgFailed(true)}` → fallback con inicial o icono

### Estado del bundle

- `tsc --noEmit` → 0 errores.
- `npm run build` → OK (dist/ con 974 archivos).

### Verificación visual de la cadena de iconos (`.workbuddy-ai/preview/panel-icons.html`)

Auditoría del catálogo: **565 entradas, 525 con `icon`, 40 sin `icon`, y 0 iconos
declarados ausentes de `public/n8n-icons/` (409 archivos)**. Conclusión: la reserva
no existe para 404s, existe para los 40 nodos que legítimamente no declaran icono
(`AlibabaCloud`, `Anthropic`, `Confluence`, `Cron`, `Function`, los LangChain sin
`.node.json`, …).

La cadena real de `PanelItem` tiene 4 brazos y siempre termina pintando algo:

1. `n8nIcon` presente y el archivo carga → `<img>` (logo real).
2. `n8nIcon` declarado pero el archivo da 404 → **Lucide** (`n8nInitial` es
   `undefined` justo porque `e.icon` era truthy). Este era el brazo que se rompía.
3. Sin `n8nIcon` → badge con la inicial coloreada (`initialBadge`).
4. Sin icono ni inicial (ítems escritos a mano) → Lucide del grupo.

El arnés carga la **hoja de estilos real** (`styles.css`, sin redeclarar
`.fsp-item` localmente) y replica el marcado exacto de `PanelItem`, con un sondeo
que mide cada `.fsp-item-icon`: `child`/`kind`/`painted`. Resultado: **9/9 filas
con icono — 3 logo, 3 inicial, 3 lucide — `vacios: 0`, veredicto `ALL-OK`**. La
columna "ANTES" (handler viejo `display:none`) reproduce los tres cuadrados
vacíos que el usuario reportó.

Lección: para verificar un fallback de React en un arnés estático hay que
**replicar la lógica de estado** (aquí `imgFailed` → swap del nodo), no solo el
marcado; y hay que enlazar el CSS compilado real en vez de redeclarar la clase,
o se mide una aproximación en vez del producto.
